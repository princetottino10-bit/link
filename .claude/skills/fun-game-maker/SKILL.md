# おもしろゲーム作り

目的は「ルールとして成立するゲーム」ではなく「**また遊びたくなるゲーム**」を作ること。

調査の結論はシンプルで、面白さは次の 2 つでほぼ決まる。
1. **毎手番に「何かを諦める」選択がある**（トレードオフがあり、最善手が状況で変わる）
2. **勝敗の見通しはあるのに、最後まで確定しない**（逆転の筋が残る・消化試合がない）

そして面白さの大部分は、カード 1 枚の強さではなく**構造**で決まる。構造とは「得点の配り方」「攻撃対象の書き方」「手番の同期のさせ方」「終わり方」の 4 つ。カードを作り込む前にここを決める。

根拠・出典・実例は [references/research-report.md](references/research-report.md)（調査レポート全文）にある。迷ったら該当章を読む。

## 進め方

1. **狙う体験を決める** → 2. **構造を決める** → 3. **カード/勢力を作る** → 4. **机上テスト・シミュレーションで壊す** → 5. **文書化** → 6. **（必要なら）デジタル化** → 7. **人とテスト → 改訂**

ユーザーがどの段階にいるかを見て、途中から入ってよい。段階ごとに成果物を見せ、方向を確認してから次へ進む。

## 1. 狙う体験を決める

最初に次を言葉にする（1 行ずつ）。ここが曖昧だと、後でいくらカードを足しても面白くならない。

- **狙う感情を 2〜3 個**（MDA の 8 分類：感覚・空想・物語・挑戦・仲間意識・発見・表現・暇つぶし から選ぶ）
- **核の判断**：ゲームを 1 つの単純で面白い判断で説明できるか（例：Snap の「賭けるか降りるか」、Compile の「表で効果か裏で値 2 か」、Hanamikoji の「どう分けて渡すか」）
- **核の瞬間**：プレイヤーが声を出すのはどこか（読みが刺さる／連鎖で盤面が動く／苦渋の選択と苦笑い）
- **政治を楽しむゲームか、純粋な腕比べか**（多人数戦なら必ず先に決める。キングメイキングへの態度が変わる）

既存ゲームを混ぜるなら [references/mashup-method.md](references/mashup-method.md) を読む：骨格は片方、味は両方から 1〜2 個ずつ。

ユーザーに聞くのは**答えで設計が変わるもの**だけ（人数・時間・遊ぶ場所・対象）。それ以外は妥当な初期値で進めて「仮」と明記する。

## 2. 構造を決める

### 高評価作の 10 パターンから 2 つ以上を組み合わせる

多用途カード／レーン・ゾーン多数決／コミットのタイミング／分けて選ばせる／相手に開けてしまう共有の場／伏せ札・ブラフ／モジュール混合（派閥を混ぜる）／複数勝利条件／綱引きトラック／短時間・小さな山札。
各パターンの代表例と効果はレポート「高評価作は10個の共通パターン」の表を参照。

### 構造の既定値（理由がなければこれで始める）

- **ランダム性は入力型を主軸に**：ドローや場の公開は「判断の前」に置く。判断の後のダイスは山場の演出だけ
- **確実に終わる仕組み（慣性）と上限時間**：ラウンド上限＋残りラウンドの常時表示。終盤ほど得点・緊張が上がる曲線を作る
- **ランナウェイリーダー対策は「向かい風」と複数の勝ち筋で**。露骨な追い上げ補正は上手いプレイを罰するので最後の手段
- **先攻/席順の補正は入れたら必ず測り直す**（補正は過剰になりやすい）
- **フィールバッド効果は否定より遅延**：破壊・打ち消し・手札破壊より「手札に戻す」「一時的に裏向き」。相手に何もさせない効果は作らない

### 3 人以上（特に 4 人）なら必ず入れる

多人数戦の失敗要因は**キングメイキング・リーダー叩き・ダウンタイム**の 3 つ。詳しくは [references/multiplayer.md](references/multiplayer.md)。最低限：

- **攻撃対象は「場所」単位**（共有の基地・レーン）か「各対戦相手」「隣の人」。「好きな 1 人を選ぶ」は少数にし、使うなら「最も得点の高い人」など自動で決まる形に
- **全順位に得点を配る**（例：5/3/2/1）。最下位にも参加理由を残す
- **全員同時に伏せて配置 → 一斉公開**（Snap / 7 Wonders 型）。交互手番なら他人の手番中にもできることを作る
- **得点は「おおよそ分かるが正確には分からない」**（秘密の終了時ボーナスなど）
- **2 対 2 のチーム戦モード**を検討する（勝敗共有・手札は非公開・合図は制限）。キングメイキングが構造的に消える

## 3. カード/勢力を作る

詳細と出典は [references/card-design.md](references/card-design.md)。要点：

- 勢力は**中心の動詞 1 つ**（増やす・動かす・引く・裏返す…）と**意図的な弱点 1 つ**で定義する。「できないこと」で個性が立つ
- 勢力ごとに「得意なこと／苦手なこと／勝ち方」の 3 行を書く（Compile の「プロトコル概要がない」批判への対策にもなる）
- **深さ ÷ 複雑さ** で評価する。文面は短く（日本語 20〜30 字目安）、強さは組み合わせから生まれるように。**2 回説明が要るカードは作り直す**
- 共通の動詞（引く・削除・反転・移動…）を先に定義し、カードはその組み合わせで書く
- 特定の勢力名を参照するカードは避け、シナジーは動詞同士の掛け算から生まれるようにする（プレイヤーに発見させる）
- **コストカーブ**：効果を共通の通貨で値付けし外れ値を探す。基準値（例：裏向き＝値 2）に対する損得を表にする。**迷ったら弱めに**
- 目標は「**すべてのカードに居場所がある**」。どこにでも入るカードは強さより汎用性を理由に削る

## 4. 机上テスト・シミュレーションで壊す

文書化の前に、自分で全員分を何手番か回し、結果をユーザーに正直に報告する。チェックリストは [references/fun-checklist.md](references/fun-checklist.md)。

- 1 ゲームの長さ（4 人で 20〜30 分、スマホなら上限表示）、無限ループ、何もできない手番、1 枚で決まる壊れカード
- 数値が絡むなら **Python/JS で簡易シミュレーター**を書いて数百〜数千回回す（[references/playtest.md](references/playtest.md)）。見るのは：席別勝率・勢力別勝率と相性表・首位交代の回数・中盤首位がそのまま勝つ割合・カード別の採用率と勝率
- 4 人戦の席順の偏りは人間のテストでは見えない（±2 ポイントで測るには各席約 1,800 試合）。**シミュレーションで測る**
- シミュレーションは極端な違反の検出用。面白さ・フィールバッド・分かりやすさは人間にしか測れない

## 5. 文書化

成果物はファイルで残す。カードデータは CSV/JSON を**単一の情報源**にすると、紙版・Web 版・シミュレーターを同じデータから作れる。

- `RULES.md`：概要 / 内容物 / 準備（盤面図） / 手番の流れ / 得点と勝利 / 用語の定義（対象・タイミング・同時発生の順） / 調整メモ
- `CARDS.md`（＋ `cards.json`）：勢力ごとの 3 行サマリーと表 / その他のカード / 組み合わせ例
- バージョン番号を付け、数値が仮であることを明記する

## 6. デジタル化（スマホ・オンライン対戦）

[references/digital-build.md](references/digital-build.md) を読む。要点：ルールエンジンと画面を分ける／ホストかサーバーが状態を持ち、各人には見える情報だけ送る／ルームコード＋共有リンク／同時配置・一斉公開とボタン一体型タイマー／何もできないときは自動スキップ／切断時は猶予の後に Bot が代行し、全員に通知して復帰で席を返す／盤面・合計値・順位は常時表示して計算させない。

## 7. 人とテスト → 改訂

[references/playtest.md](references/playtest.md) の段階表に沿う。友人は気を遣って褒めるので、**感想より行動を記録**する（身を乗り出す・声が出る・自分の番以外にスマホを見る・「もう 1 回」と自分から言う）。改訂は「最大の問題を 1 つ選び、まず削る案から」。1 回に変えるのは 1〜2 か所。

## 伝え方

- ユーザーは遊ぶ人であり作る人。理論名より「この瞬間がおもしろい」「ここで迷う」「ここで待たされる」という言葉で説明する
- 案は 1 つに絞って推す。比較するときも推しを明示する
- 「おもしろくなりそうな点」と「心配な点」を両方正直に言う。推論と出典のある知見は区別する
