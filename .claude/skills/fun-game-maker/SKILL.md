# おもしろゲーム作り

目的は「ルールとして成立するゲーム」ではなく「**また遊びたくなるゲーム**」を作ること。
ルールの量を増やすより、**おもしろい瞬間**をはっきりさせて、そこに向かって全部を削っていく。

## 進め方の全体像

1. **おもしろさの核を決める** → 2. **骨組みを組む** → 3. **カード/コンテンツを作る** → 4. **机上テストで壊す** → 5. **文書化** → 6. **（必要なら）デジタル化**

ユーザーがどの段階にいるかを見て、途中から入ってよい。段階ごとに成果物を見せて、方向が合っているか確認してから次へ進む。

---

## 1. おもしろさの核を決める

最初に、次の 3 つを 1 行ずつ言葉にする。ここが曖昧だと、あとでいくらカードを足してもおもしろくならない。

- **核の瞬間**：プレイヤーが「うおっ」と声を出すのはどの瞬間か（例：裏向きカードを表にして逆転する、ベースが壊れる直前の駆け引き）
- **主な決断**：毎手番、何と何で迷うのか（迷わない手番はつまらない）
- **相手との関わり**：相手の行動にどう反応できるのか（ソロパズルの並走にしない）

### 既存ゲームを混ぜるとき（マッシュアップ）

「A と B を混ぜたい」と言われたら [references/mashup-method.md](references/mashup-method.md) を読む。
要点：各ゲームを「骨格（盤面・手番・勝ち方）」と「味（そのゲームらしさを生む仕組み）」に分解し、**骨格は片方、味は両方から 1〜2 個ずつ**だけ取る。全部足すと重くなる。

### ユーザーに聞くこと（決まっていなければ）

人数・1 ゲームの時間・遊ぶ場所（紙 / スマホ同じ端末 / オンライン）・対象（ガチ勢 / 友達とワイワイ）。
聞くのは**答えで設計が変わるものだけ**にし、それ以外は妥当な初期値で進めて「仮」と明記する。

## 2. 骨組みを組む

決めるもの：内容物 / 準備 / 手番の流れ / 得点・勝利条件 / 終了条件。

設計の目安：
- **手番は 1 アクションで終わる**くらい短く（特にスマホ。待ち時間が長いと離脱する）
- **反応の猶予**を作る：決着の直前に相手が 1 手番だけ対応できるタイミングを置くと駆け引きが生まれる
- **勝ち筋を 2 本**用意すると戦略が分かれる（例：VP 勝利 と 特殊勝利）。ただし片方が明らかに速くならないよう数値で確認する
- **先攻有利**は必ず補正する（後攻の手札 +1、初期リソース差など）
- **公開情報と非公開情報**を決める。隠し情報（裏向き・手札）はブラフを生む一方、デジタル化では通信で隠す必要がある

## 3. カード / コンテンツを作る

- 派閥・デッキ・キャラなどの単位ごとに**テーマ = 動詞**を 1 つ決める（例：海賊 = 移動、ゾンビ = 捨て札から戻る）。テーマが動詞で言えると、効果がぶれない
- 効果の動詞（引く・削除・反転・移動…）を**共通用語として先に定義**し、カードはその組み合わせで書く
- **コスト/値と効果の強さを反比例**させる（値が低いカードほど強い効果、高いカードは効果なし or 弱い）
- 各派閥に「単独で回るカード」と「他の派閥と組んで光るカード」を両方入れる
- 「〜してもよい」と「必ず〜する」を意識的に使い分ける（強制のデメリットは味になる）

詳しいチェック項目は [references/fun-checklist.md](references/fun-checklist.md)。

## 4. 机上テストで壊す

文書化の前に、自分で何手番か**実際に回してみる**。頭の中で 2 人分プレイし、次を確認して結果をユーザーに報告する。

- 1 ゲームが何手番・何分くらいで終わるか（耐久値や目標点の数字を逆算して検算する）
- 先攻と後攻の差
- **無限ループ・連鎖**（追加プレイ → 追加プレイ…、ドロー → 追加プレイ…）がないか
- 何もできない手番（手札事故）がどれくらい起きるか
- 1 枚で試合が決まる壊れカードがないか

カード枚数が多い・数値が絡むときは、Python か JS で**ランダムプレイの簡易シミュレーター**を書いて数百回回し、ゲーム長・先攻勝率・勝利条件ごとの発生率を出す。完璧なルール実装はいらない。数字の当たりをつけるのが目的。

見つかった問題は隠さず書き、直し方の案を一緒に出す。

## 5. 文書化

成果物はファイルで残す（チャットだけで終わらせない）。基本は次の 2 つ：

- `RULES.md`：概要 / 内容物 / 準備（盤面図） / 手番の流れ / 得点と勝利 / 用語の定義 / 調整メモ
- `CARDS.md`：派閥ごとの表（値・名前・効果） / その他のカード（ベースなど） / 組み合わせ例

用語は表にまとめ、「対象にできるのはどのカードか」「同時に起きたらどの順か」まで書く。ここが曖昧だとデジタル化で必ず詰まる。
バージョン番号（v0.1 など）を付け、数値が仮であることを明記する。

## 6. デジタル化（スマホ・オンライン対戦）

Web で遊べるようにするときは [references/digital-build.md](references/digital-build.md) を読む。
要点：ルールエンジン（純粋な状態遷移）と画面を分ける / ホストがゲーム状態を持ち、相手には見える情報だけ送る / サーバーなしなら WebRTC P2P（PeerJS）+ ルームコード / 縦持ち・片手操作前提の画面。

## 伝え方

- ユーザーは遊ぶ人であり作る人。専門用語より「この瞬間がおもしろい」「ここで迷う」という言葉で説明する
- 案は 1 つに絞って推す。比較するときも推しを明示する
- 「おもしろくなりそうな点」と「心配な点」を両方正直に言う
